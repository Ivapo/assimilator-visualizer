2. **The fetch** (`probe.sql`, then `fetch-exact-{1,2}.sql`):
   ```sql
   LOAD httpfs; LOAD spatial; SET s3_region = 'us-west-2';
   COPY (SELECT id, height, num_floors, geometry
         FROM read_parquet('s3://overturemaps-us-west-2/release/2026-09-23.1/theme=buildings/type=building/*.parquet')
         WHERE bbox.xmin <= -73.9643086 AND bbox.xmax >= -73.9938413
           AND bbox.ymin <= 40.7740495 AND bbox.ymax >= 40.7544211
         ORDER BY id)
   TO 'exact-1.geojson' WITH (FORMAT GDAL, DRIVER 'GeoJSON');
   ```
   - The first probe's bbox was rounded to the nearest 1e-7, not outward. So it was up to
     1e-7° (≈ 1.1 cm) smaller on three sides. It gave the same 4,336 features, byte for byte
     after the header.
   - Wall time per fetch (`/usr/bin/time -p`): 140.9 s, 121.5 s and 145.3 s, with user CPU
     8–14 s. It is network-bound.
   - The output is a `FeatureCollection` with `"crs": urn:ogc:def:crs:OGC::CRS84`, `[lng,
     lat]`, 7 decimals, and properties `id`, `height`, `num_floors`.
   - DuckDB prints an axis-order warning; `SET geometry_always_xy = true` states the order
     that was used.
   - **GDAL writes the output file's stem as the collection's `"name"`.** `exact-1` and
     `exact-2` differ only on that line. With the line set to `"name": "buildings"`, all
     three outputs hash to
     `561a615d6fa77bbef482b99f9f771b8b12f5891a46e661015e034b833d2bce47`, 2,140,989 bytes.
